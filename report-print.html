ABSTRACT

MindGrid is an interactive puzzle arcade and aptitude-practice application that brings four classic problem-solving games together behind one interface, pairs each of them with an algorithmic solver, and reports measured search performance in a built-in benchmark dashboard. The primary build is a responsive front-end web application written in semantic HTML, CSS and plain JavaScript; a companion C++17 console program implements the same four modules with the same algorithms and a locally stored player profile.

The four modules exercise three recognised aptitude areas. Sudoku and the N-Queens Tour develop logical reasoning and constraint deduction: the player works with candidate sets, elimination and placement rules, and the application demonstrates the same reasoning mechanically through bit-mask backtracking. Connect Four and 2048 develop quantitative reasoning: the player evaluates line threats, merges powers of two and reasons about scores, while the application demonstrates game-tree search with alpha-beta pruning and a weighted heuristic evaluation. The benchmark dashboard develops data interpretation: it presents elapsed time, node counts, pruning cut-offs and solution counts that must be read and compared rather than taken as a single number.

The distinguishing characteristic of the project is its local-first design. The browser build has no framework, no build step, no package installation and no server; progress is stored in localStorage under a single key. The console build stores the same summary in a plain text profile file. Every solver runs on the user's own device, and every measurement is reported as an observation of that run rather than as a fixed performance claim.

This report documents the project background, problem statement, objectives, methodology, architecture, module design, algorithm analysis with worked examples, the dedicated Image Table of structured matrices, user interface evidence, data design, comparison tables, gap analysis, evaluation criteria, limitations and conclusion. All numeric results quoted in the report were obtained from the submitted source and from actual runs of that source on the development machine.

1. PROJECT TITLE AND BASIC INFORMATION

Project Overview

Project title: MindGrid: An Interactive Puzzle Arcade, Aptitude Module and Algorithm Benchmark Web Application.

MindGrid is a browser-based arcade and practice environment for four puzzle problems that are regularly used to develop and examine aptitude: Sudoku for constraint deduction, the N-Queens Tour for combinatorial placement reasoning, Connect Four for lookahead and evaluation reasoning, and 2048 for numeric merging under spatial constraints. Each module offers an interactive play mode, validation of every move against the rules of the game, a solver or a move suggestion, and a measured report of how much search work the solver performed. A shared navigation shell connects the modules, a locally stored profile summarises progress, and a benchmark screen runs all four solvers and presents their timings side by side.

The project is delivered as two implementations of the same idea. The first is a static front-end application in the web/ directory, written without a framework, a build step or a package manager. The second is a single-translation-unit C++17 console program in main.cpp that reproduces the four games, the four algorithms and the profile summary in a terminal. Both builds are self-contained and run locally.

2. EXECUTIVE SUMMARY AND PROBLEM STATEMENT

Executive Summary

MindGrid shows that a multi-module aptitude practice application can be built entirely as a static front-end project. A single navigation shell exposes four games, a profile summary and a benchmark screen. The browser renders the shell from index.html, styles it from styles.css, and drives everything else from app.js, a 378-line module written as one immediately invoked function with no dependencies. State for each game is held in a plain object, each view is rebuilt from that state, and a single delegated click listener plus a keyboard listener route all interaction. Nothing is reloaded when the player moves between modules.

The algorithmic layer is the part that turns the arcade into a teaching instrument. Sudoku is generated by seeding three independent bands, completing a full random grid, and then removing cells only while the puzzle keeps exactly one solution; the solver picks the cell with the fewest candidates at every step. Connect Four searches a bounded game tree with alpha-beta pruning over a fixed centre-first move order and scores positions with a weighted window count. N-Queens enumerates arrangements with three bit masks and reports the exact number of solutions for the selected board size. 2048 evaluates each of the four possible slides with a weighted heuristic and plays the best one. The benchmark screen runs all four and prints the measured cost of each.

Everything runs on the user's device. Progress is written to localStorage under one key, the console build writes the same summary to profile.txt, and the console build measures solver time with a monotonic clock in microseconds. No personal data leaves the machine and no network service is required for any feature of either build.

Problem Statement

Aptitude practice material is usually presented in one of two disconnected forms. Puzzle collections give the player a grid and an answer key but no explanation of how the answer was reached. Algorithm demonstrations give the search procedure in isolation, often as a console snippet, without an interface a player can actually interact with, and without any record of progress. As a result, a learner who solves a Sudoku puzzle learns nothing about why a candidate was eliminated, and a learner who reads a minimax example never sees how many nodes the search actually visited.

The problem addressed by this project is therefore to build one application in which the same four problems can be played interactively, solved algorithmically, and measured locally, so that the reasoning a player performs by hand and the search the program performs by machine can be compared directly. The application must remain simple to run, must not depend on a server, and must report only measurements it can honestly produce.

Project Objectives

  • • Provide one consistent interface for four distinct puzzle modules, with navigation, status feedback and a shared visual identity.
  • • Enforce the rules of each game completely: no illegal Sudoku placement, no floating Connect Four disc, no attacked queen and no double merge in 2048.
  • • Implement four different algorithmic approaches so that the modules illustrate constraint satisfaction, game-tree search, combinatorial enumeration and heuristic evaluation rather than repeating one technique.
  • • Generate Sudoku puzzles that are guaranteed to have exactly one solution at every difficulty level.
  • • Report solver effort, not only solver output: elapsed time, nodes visited, alpha-beta cut-offs, solution counts and suggested moves.
  • • Keep a local record of progress and best results in both builds, without accounts or a server.
  • • Verify the engine behaviour automatically with a test suite that runs against the same code the browser executes.
  • • Keep the browser build free of any framework, package installation or build pipeline so that it can be opened directly.

Intended Users

The primary users are students preparing in logical reasoning, quantitative aptitude and data interpretation who want an interactive practice environment rather than a printed question bank, and who can read a worked deduction. The secondary users are instructors and reviewers demonstrating search techniques: the benchmark screen and the console build give a live, measurable example of backtracking, pruning and heuristic evaluation without any setup beyond opening a file or running one command.

Expected Learning Outcomes

A user who works through the modules and the worked examples in Section 5 should be able to: compute the candidate set of a Sudoku cell from row, column and box occupancy; explain why a minimum-remaining-values choice reduces search; evaluate a Connect Four window and explain why a defence weight is larger than the matching attack weight; state the number of solutions of a small N-Queens board and why the search space is far smaller than the naive placement count; compute the score produced by a 2048 slide; and interpret a benchmark card that shows a time together with a node or solution count.

3. CASE STUDY DESCRIPTION AND METHODOLOGY

Case Study Description

The case study is the design, implementation and local operation of MindGrid in two environments: a browser as a static front-end application, and a terminal as a C++17 console program. The browser case was chosen because an aptitude practice tool has to be opened instantly to be used often, which rules out an install step; the console case was chosen because solver behaviour is easiest to inspect when output is plain text and the same measurement loop can be seen without a rendering layer.

Both builds were developed against the same four problem definitions so that a result in one environment can be checked against the other. The console build is not a wrapper around the browser build: each implements its own state representation and its own solver, and the report compares them directly in Table 9.2, including the differences in evaluation weights and search depth that were tuned separately for each environment.

Development Methodology

  1. 1. Requirement identification: list the modules to practise (four games), the reasoning each should expose (candidate elimination, safe placement, lookahead, merge arithmetic), the controls each needs (undo, reset, hint, solve, difficulty) and the measurements worth reporting.
  2. 2. Rule and state modelling: fix the board representation for each module before writing any interface code — an 81-cell flat array for Sudoku, a 6 by 7 grid for Connect Four, one column per row for N-Queens, and a 4 by 4 matrix for 2048.
  3. 3. Algorithm design: choose one distinct technique per module, and decide what each solver can honestly report: a solved grid for Sudoku, a column plus node and cut-off counts for Connect Four, a solution count and first arrangement for N-Queens, and a direction for 2048.
  4. 4. Interface design: prepare the navigation shell, the board layouts, the side panels, the status messages, the responsive rules and the keyboard controls in styles.css and index.html.
  5. 5. Application logic: implement the engines, rendering and event routing in app.js as one immediately invoked function, keeping each engine in its own commented section so that it remains identifiable.
  6. 6. Console parity: implement the same four modules behind one abstract Game interface in main.cpp so that the menu and the benchmark loop can treat all four polymorphically.
  7. 7. Persistence: add a single localStorage key for the browser profile and a three-field text file for the console profile, with the fastest solver time stored as a running minimum.
  8. 8. Verification: write automated engine tests that load app.js itself into a simulated DOM and assert rule correctness, then run a manual pass over navigation, responsiveness and solver completion.
  9. 9. Documentation: record the run instructions in web/README.md and assemble this report from the implemented behaviour rather than from an intention.

Local Setup Procedure

Browser build: open web/index.html in a modern desktop or mobile browser. There is no installation, no dependency resolution and no build command. Local storage must be enabled if the progress summary is to survive a reload.

Browser:   open web/index.html
Tests:     node --test .\web\tests\engines.test.cjs
Console:   g++ -std=c++17 -O2 -Wall -Wextra -pedantic main.cpp -o mindgrid

Console build: compile main.cpp with any C++17 compiler using the command above. The program presents a numbered arcade menu; option 6 runs the full benchmark suite. The build produces no warnings under -Wall -Wextra -pedantic. ANSI colour escapes are used for the interface, so a terminal that understands virtual terminal sequences displays the intended colours and any other terminal still displays correct text.

Testing and Verification Methodology

Correctness was verified at two levels. The automated level runs the real browser engine code inside a simulated DOM: the test harness reads app.js, injects a hook that exposes the engine functions, and executes the file with a fake document, fake storage and captured event listeners. This means the tests exercise the same functions the browser uses rather than a reimplementation. The manual level covers what the automated tests cannot: visual layout at narrow widths, pointer and keyboard interaction, and profile persistence across reloads.

Design principle: the word API is not used for a network layer. The browser build contains no fetch call, no endpoint and no remote data source. Browser Data Flow

  2. 2. Initialise: the profile is read defensively — safeRead() parses the stored JSON inside a try block and returns an empty object on any failure — so a corrupted or absent entry cannot stop the application.
  3. 3. Render: renderHome() writes the overview into the #view section and saveProfile() refreshes the solved count shown in the sidebar.
  4. 4. Interact: one delegated click listener on document inspects the clicked element for data-screen, data-cell, data-value, data-difficulty, data-col, data-qrow or data-action attributes and calls the matching handler. Delegation is used deliberately because every view replaces the whole innerHTML of #view.
  5. 5. Update state: the handler mutates the relevant state object (sudoku, connect, queens or game2048), which is the single source of truth for what is drawn.
  6. 6. Re-render: the active view is rebuilt from the new state, so the interface can never show something the state does not contain.
  7. 7. Persist: after a solved puzzle, a 2048 move or a timed solver run, saveProfile() serialises the profile back to localStorage.

Console Data Flow

main() loads profile.txt, constructs all four game objects once so that a puzzle or board survives between menu visits, and enters the arcade menu. A game selection dispatches through the abstract Game pointer to playInteractive() or runAISolverBenchmark(); the benchmark suite iterates an initialiser list of the four pointers. Every timed solver invocation is wrapped in the generic Utils::benchmarkUs(), which reads a monotonic clock before and after the call and returns whole microseconds; the result is passed to PlayerProfile::recordSolve(), which increments the solved count, keeps the smallest time seen, and writes the file. The profile is written again on exit.

5.2 Sudoku — Logical Reasoning Module

Representation. The board is a flat array of 81 values where 0 means empty. Alongside it the engine keeps three arrays of nine integers: one mask per row, one per column and one per 3 by 3 box. A mask uses bit v−1 to record that digit v already appears in that unit, so occupancy tests are single bitwise operations rather than scans. The box containing cell (r, c) is obtained by the formula used in both builds:

b(r, c) = ⌊br / 3⌋ × 3 + ⌊bc / 3⌋ FULL = 2⁹ − 1 = 511

Candidate computation. A digit is legal in a cell exactly when it is absent from all three units that meet there. With R(r), C(c) and B(b) denoting the three masks, the candidate set of a cell is:

Cand(r, c) = FULL − ( R(r) ∪ C(c) ∪ B(b(r, c)) )   n = |Cand(r, c)| = popcount( Cand(r, c) )

The engine counts the candidates with Brian Kernighan's popcount, which clears the lowest set bit at every step and therefore runs once per candidate rather than once per digit: for (m = mask; m; m &= m − 1) count++. This matters because the count is computed for every empty cell at every node of the search.

Solver. The solver is a recursive backtracking search that chooses, at each node, the empty cell with the fewest candidates — the minimum-remaining-values heuristic. A cell with no candidates makes the node fail immediately, and a cell with exactly one candidate is committed at once without further scanning. Candidates are then tried one at a time; before recursing, the digit is added to the three masks, and on return it is removed, which keeps the mask arrays consistent with the grid at every depth.

Worked example of one deduction step. Consider an empty cell at row 3, column 5 (1-based) in a partially filled grid. Suppose the row already contains {2, 4, 7, 9}, the column contains {1, 4, 7, 8} and the box contains {4, 7, 5}. The union of these is {1, 2, 4, 5, 7, 8, 9}, so the candidate set is {3, 6}. If the same row's box partner later removes 6, the cell has exactly one candidate and the solver commits 3 without searching. This is precisely the naked-single case that both builds detect and resolve before any branching, and it is the same step a player is taught to make by hand.

Generation and uniqueness. A puzzle is produced in three stages. First the three diagonal bands of boxes are filled with shuffled digits; because those boxes share no row or column, each choice is independent and the grid always remains completable. Second, the completed grid is filled by running the same solver with a randomised candidate order, which yields a random valid solution. Third, cells are visited in shuffled order and each is blanked only if the resulting puzzle still has exactly one solution; that test re-solves a copy of the puzzle with the search capped at two solutions, so the generator never needs to enumerate the whole solution space.

5.3 Connect Four — Lookahead and Quantitative Evaluation Module

Representation and rules. The board is a 6 by 7 grid. A drop in column c lands in the lowest empty row of that column, found by scanning upward, and a column whose top cell is occupied rejects the move. A win test walks, from each of a player's own cells, the four direction vectors (0,1), (1,0), (1,1) and (1,−1), counting consecutive discs; four or more in any direction is a win. The number of distinct length-4 windows on this board is 69: 24 horizontal, 21 vertical and 24 diagonal, which is the quantity the evaluation function sums over.

Evaluation function. A leaf position is scored as a centre-control term plus a sum over all 69 windows. Only windows that contain discs of one player and none of the other contribute; a window holding both colours is dead and scores zero. Writing a for the number of AI discs and h for the number of human discs in a window:

E = w₀ · Aₔₑₙₜₑₐ + Σᴡₙₔₙₔₓ [ f(a) − g(h) ] where f applies only if h = 0 and g applies only if a = 0

Table 5.3: Evaluation weights used by the two builds.

The asymmetry between +90 and −110 is the most instructive number in the module. Because the magnitude of the defensive penalty exceeds the offensive bonus for the same line length, the agent blocks an opponent threat in preference to building its own when both are equally close to completion. A player who reviews the evaluation table can predict that behaviour before seeing a single move, which is exactly the kind of reasoning the quantitative module is meant to practise.

Search. The move choice is a minimax search with alpha-beta pruning. At each node the columns are tried in the fixed centre-first order 3, 2, 4, 1, 5, 0, 6, which places the most valuable columns early and therefore produces cut-offs earlier. The browser build searches to depth 5 below the move under consideration; the console build uses depth 6, which is why its output labels the task a depth-7 move counting the root. Terminal values dominate leaf values by three orders of magnitude, so a forced win is never traded for a favourable evaluation.

Complexity arithmetic. With seven columns and depth d, a full tree would contain 7ᵈ nodes: 16,807 at depth 5 and 117,649 at depth 6. Alpha-beta pruning with good move ordering reduces the effective cost to the order of 2 · b^(d/2), about 252 nodes for depth 5 in the ideal case. The observed run reported in Section 7 visited 1,688 nodes with 496 cut-offs in the browser and 24,838 nodes with 6,654 cut-offs in the console, which sits between those two bounds and shows the ordering helping without being perfect.

Worked example. A window containing three yellow AI discs and an empty fourth cell, with no red disc, scores +90. A window containing three red discs and one empty cell scores −110. If the AI has both, the total for those two windows is −20, and the search will prefer the line that removes the red threat, because eliminating −110 gains more than securing +90. This single comparison is the reason the automated test asserts that the agent blocks a three-in-a-row rather than extending its own.

5.4 N-Queens Tour — Combinatorial Reasoning Module

Representation. One queen occupies each row, so a placement is a list of n column indices. Attacks are tracked with three bit masks of n bits: the columns already used, the diagonals attacking the next row from the left, and the diagonals attacking it from the right. For a board of size n the mask of all squares is FULL = 2ⁿ − 1, and the free squares of the current row are:

available = FULL − ( cols ∪ left ∪ right ) pick lowest bit: bit = available ∩ (−available)

recurse with: cols' = cols ∪ bit, left' = ( (left ∪ bit) ≲ 1 ) ∩ FULL, right' = ( right ∪ bit ) ≳ 1

The expression available & −available isolates the lowest set bit in one operation, and the shifted masks express the fact that a diagonal threat moves one square sideways as each row is descended. Both builds use this formulation; the console build uses 32-bit masks, which is the reason the interactive board size is limited to 14 rows.

Search and counting. The recursion proceeds row by row. When the last row is filled, one solution is counted; the browser build additionally retains the first arrangement it finds so that the player can see a complete placement. Because the search enumerates all valid arrangements, the count it returns for a given n is exact and can be checked against the published sequence, which the automated tests do for n = 4, 8 and 14.

n Free placement of n queens on n² squares One per row (nⁿ) Permutations of columns (n!) Valid solutions found
4 C(16, 4) = 1,820 4⁴ = 256 4! = 24 2
8 C(64, 8) = 4,426,165,368 8⁸ = 16,777,216 8! = 40,320 92
14 C(196, 14) ≈ 4.6 × 10¹⁷ 14¹⁴ ≈ 1.1 × 10¹⁶ 14! = 87,178,291,200 365,596

Table 5.4: Search space reduction for three board sizes.

Worked example for n = 4. Place the first queen in column 1 of row 0. Row 1 then has columns 0, 1 and 2 attacked, so only column 3 is safe. With queens at rows 0 and 1 in columns 1 and 3, row 2 has only column 0 free, and row 3 only column 2. The resulting arrangement [1, 3, 0, 2] is one of the two solutions the solver counts, and the automated test asserts exactly this list. The same reasoning, applied by hand, is the safe-square test the interface enforces on every click: a column conflict or a diagonal conflict of the form |column difference = row difference| is rejected.

Interactive rule. The player places one queen per row in order; the interface marks attacked squares, refuses an unsafe square, allows the last queen to be undone, and offers both a solve action, which fills a complete arrangement, and a count action, which reports the total number of arrangements for the selected size without placing anything.

5.5 2048 — Quantitative Aptitude Module

Representation and merge rule. The board is a 4 by 4 matrix whose values are powers of two, with 0 for an empty cell. A slide moves every tile as far as possible in the chosen direction and merges equal neighbouring pairs in travel order, with the rule that a tile produced by a merge cannot merge again in the same move. Each merge adds the value of the resulting tile to the score, so the score is the sum of all merged results rather than the sum of the tiles on the board.

tile value = 2ᵏ for k ≥ 1 merge: 2ᵏ + 2ᵏ = 2ᵏ⁺¹, score += 2ᵏ⁺¹ spawn: 2 with probability 0.9, 4 with probability 0.1

Worked example of one slide. The row [2, 2, 2, 2] slid to the left becomes [4, 4, 0, 0] with a gain of 8, not [8, 0, 0, 0]: the first pair merges into 4 and the second pair merges into 4, and neither resulting tile is allowed to merge again. The automated test asserts exactly this result and the gain of 8, because it is the single rule that distinguishes a correct implementation from a naive one. A vertical example from the same test, [2, 2, 4, 0] moved up, yields [4, 4, 0, 0].

Score arithmetic. Reaching the 2048 tile from 2-valued spawns alone requires 1,024 spawned tiles and merges at ten levels. At the level that creates a tile of value 2ᵏ, exactly 2048 / 2ᵏ merges occur, each contributing 2ᵏ, so every level contributes 2,048 to the score:

minimum score for one 2048 tile = Σ (k = 2 … 11) [ (2048 / 2ᵏ) × 2ᵏ ] = 10 × 2048 = 20,480

This identity is a compact arithmetic exercise in its own right and explains why a player's score is far larger than the largest tile on the board. When a 4 is spawned instead of a 2, one merge at the lowest level is skipped and the total falls slightly below 20,480.

Heuristic move selection. The helper evaluates each of the four directions by applying the slide to a copy of the board and scoring the result with a weighted linear function of four positional features. The move value adds a small share of the immediate gain:

Feature Weight Definition Behaviour it produces
Empty cells +260 Count of cells holding 0 Dominant term: keeping the board open is valued above everything else
Monotonicity −14 Sum over adjacent non-empty pairs of |log₂ a − log₂ b| Penalises jagged boards; measured in tile exponents, not raw values
Corner bonus +180 1 if the largest tile sits in any corner, else 0 Encourages keeping the largest tile anchored rather than central
Largest tile +5 log₂ of the maximum tile value, with 1 as the floor Mild preference for progress; too small to dominate the other terms
Immediate gain +0.1 Score earned by the candidate slide, added to the heuristic Breaks ties between moves that leave equally good shapes

Table 5.5: 2048 heuristic features and weights (identical in both builds).

H(board) = 260 · E − 14 · M + 180 · C + 5 · log₂(max(1, Tₘₐₓ)) value(move) = H(after) + 0.1 · gained

Worked example. On the observed mid-game board shown in Figure 6.5, the tiles present are 16, 8, 8, 4, 2, 2 and 2 with seven empty cells. The heuristic is dominated by the empty-cell term: 260 × 7 = 1,820, while the monotonicity penalty for the same shape is a small two-digit number, and the largest tile contributes 5 × log₂ 16 = 20. Any move that keeps the board open therefore outranks any move that merges for a slightly larger tile, which is the same advice the side panel gives in words.

Limits of the helper. The selection is a greedy one-ply policy: it evaluates the immediate successor of each direction and does not model the randomness of the next spawn, so it is not an expectimax search. Undo is available because each slide pushes a whole-board and score snapshot onto a history stack, and auto-play is bounded at 50 moves per activation so that a runaway loop cannot freeze the interface.

5.6 Benchmark Suite — Data Interpretation Module

The benchmark screen runs four fixed tasks and presents one card per task. Each task is chosen so that its cost is meaningful and its correctness is checkable: a Sudoku solve of a freshly generated 42-removal puzzle, a depth-5 Connect Four search from a seeded four-disc position, an N-Queens enumeration at the currently selected board size, and a best-move scan over a fixed 4 by 4 2048 board. The browser measures with a monotonic high-resolution clock and reports milliseconds; the console measures with a steady clock and reports microseconds, except for the N-Queens task, which reports milliseconds.

Each card pairs a time with a second statistic, and that pairing is the point of the module. A time on its own invites the wrong conclusion, because the four tasks are not comparable workloads. Read with its statistic, the same number says something useful: 1,688 nodes and 496 cut-offs explain why the Connect Four card is two orders of magnitude slower than the Sudoku card, and the count of 92 arrangements explains what the N-Queens search actually produced. The fastest time seen is retained in the profile as a running minimum, so repeated runs give the player a small data set to interpret rather than a single reading.

8. LOCAL DATA DESIGN AND DATA MANAGEMENT

Data Overview

MindGrid has no database. Two kinds of data exist. The first is content: the Sudoku puzzle, the Connect Four position, the queen placements and the 2048 board, all of which are generated in memory at run time and are lost when the page closes unless the player continues playing. The second is the profile summary, which is deliberately small: three numbers in the browser and three fields in the console file. Nothing else is stored, and nothing is transmitted.

Storage Keys and Fields

Store Key or file Fields Written when
Browser mindgrid-profile-v1 (localStorage) solved — count of completed puzzles and solver runs a puzzle is completed, a solver succeeds, or a benchmark run finishes
Browser mindgrid-profile-v1 high2048 — best 2048 score seen after every slide that raises the score
Browser mindgrid-profile-v1 fastestMs — smallest timed solver run after every timeSolver() call, as a running minimum
Console profile.txt (three whitespace-separated values) gamesSolved — count of timed solver invocations inside recordSolve(), which saves immediately
Console profile.txt highScore2048 — best 2048 score seen on leaving the 2048 menu path, via recordScore()
Console profile.txt fastestSolverUs — fastest run in microseconds, −1 when unset inside recordSolve(); also written on exit

Table 8.1: Persistence keys, fields and write triggers.

The console file format is intentionally plain: the shipped profile contains the defaults 0 0 -1, which is what the loader expects when no file exists, and the loader leaves those defaults untouched rather than reporting an error. The browser reader is equally defensive: a value that cannot be parsed as JSON is discarded and replaced by the defaults, so a corrupted entry never prevents the arcade from opening.

Data Not Persisted

  • • In-progress boards: a half-finished Sudoku grid, a Connect Four position and a 2048 board are not saved between sessions.
  • • Undo history: snapshots live only in memory and are cleared by a reset.
  • • Benchmark results: the four cards are held in an in-memory array and are not written to storage; only the fastest single time survives.
  • • Generated puzzles: a puzzle cannot be exported, imported or shared, because no serialisation of a board exists.
  • • Solve counts by module: the profile aggregates all solves into one number and does not record which module produced them.

Privacy

No personal information is collected. The profile stores three numbers and no name, no identifier and no free text. Data stays inside the browser profile on the device and is removed when the user clears site data; the console profile is an ordinary file in the program's working directory that the user can inspect, edit or delete. Because both builds make no network request, there is no transmission of any local value.

Offline Behaviour

Every feature of both builds works without a network. The browser build loads three local files and needs no service, no content delivery network and no remote data; the console build needs only the compiled executable. This is a consequence of the local-first design rather than an added mode, and it means the practice tool is usable in the environments where it is most needed, including machines with no internet access.

12. LIMITATIONS AND CONCLUSION

Limitations

  • • Local-only persistence: the profile lives in one browser or one working directory, with no synchronisation, backup or multi-user support.
  • • Non-comparable timings: measurements depend on device, browser, compiler and system load, and the two builds use different units and different search depths.
  • • Greedy 2048 helper: one-ply evaluation with no model of the next spawn, so the suggestion is reasonable rather than optimal.
  • • Fixed Connect Four depth: five plies in the browser and six in the console, which is strong enough to teach lookahead but not enough to be a perfect player.
  • • Difficulty by blank count only: Sudoku levels describe how many cells are missing, not which techniques the puzzle requires.
  • • No puzzle import or export, no saved boards, and no benchmark history.
  • • Console randomness is seeded from the clock, so a generated puzzle cannot be reproduced exactly from a seed.
  • • Accessibility is partial: labels and keyboard entry exist for two modules, but there is no live announcement of board changes and no contrast control.

Conclusion

MindGrid delivers, in two independent implementations, a single interface in which four classic reasoning problems can be played, solved by an algorithm, and measured. The browser build proves that an application of this scope needs no framework, no build pipeline and no server: 378 lines of JavaScript hold four engines, four rendering paths, a benchmark suite and a profile, and the same code passes twelve automated tests executed inside a simulated DOM. The console build proves the same algorithms in a second environment, with a polymorphic game interface, a monotonic-clock measurement wrapper and a plain-text profile.

The aptitude value of the project lies in the pairing it makes possible. The candidate-set computation the solver performs is the same deduction a player is taught to write down; the evaluation weights in Table 5.3 let a reader predict the agent's behaviour before watching a move; the counting matrix in Table 7.4 shows how far the valid arrangements of a chess problem fall short of the naive placement space; and the merge arithmetic in Table 7.5 makes a well-known scoring identity verifiable from the rules alone. Read together with the benchmark cards, they turn four games into practice material for logical reasoning, quantitative aptitude and data interpretation.

The design deliberately reports only what it can observe. It states a node count when the search visited nodes, a solution count when the enumeration counted them, and a time when a clock measured one, and it declines to present a device-dependent number as a specification. That discipline, together with the local-first architecture, makes the project a dependable base for the extensions listed in Section 10 rather than a closed demonstration.

Future Scope

  • • Store benchmark history with environment metadata and present a trend view for the data interpretation module.
  • • Add a technique-based Sudoku rater and accept imported puzzle strings for validation.
  • • Replace the greedy 2048 helper with a bounded expectimax search over spawn chance nodes and compare it against the current heuristic.
  • • Add iterative deepening and a transposition table to the Connect Four search, reporting the depth actually reached.
  • • Offer optional accounts with a secure backend for cross-device progress, keeping the local profile as the offline cache.
  • • Extend accessibility with live board announcements, complete keyboard play for all modules and a contrast control.
  • • Add further modules in the same style — nonograms, Kakuro or a sliding-tiles puzzle — each with its own technique and its own reported statistic.
  • • Add a practice session mode that records attempts and accuracy per module so that progress becomes measurable.
